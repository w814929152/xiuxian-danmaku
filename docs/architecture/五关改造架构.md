## A. 关卡配置的数据化方案（ADR-1）

### ADR-1：带返回类型的静态访问器 + 一维类型化 `const` 数组，不用配置 Dictionary

**状态**：已决定并已落地（`scripts/StageCfg.gd`）

**决策**：`class_name StageCfg` 只暴露 `static func xxx(stage: int) -> T`。内部用**一维、类型化、字面量同构的 `const` 数组**存表（波次级数据按 `(s-1)*MAX_WAVES + (n-1)` 展平），用 `clampi` 做越界保护。

**备选与否决理由**

| 备选 | 为什么否 |
|---|---|
| 配置 Dictionary `{1: {"boss_hp": 1600, ...}}` | ① `const X := {复杂结构}` 报 *Cannot infer the type*；② 调用点 `int(cfg["boss_hp"])` 是 Variant 下标取值 —— 项目开了 `unsafe_property_access / unsafe_call_argument / untyped_declaration` 警告，会直接污染 0-warning 门禁；③ 键名拼错是**运行时**错误，访问器拼错是**编译期**错误。 |
| `Resource` / `.tres` | 本项目是"单场景 + 全代码生成节点"，无 `.tres` 工作流。 |
| 每关一个子类 `Stage1.gd extends Stage` | 配置是数据不是行为，不该用继承表达；5 个类 × 20+ getter 复制量远大于一张表。 |
| 二维 / 嵌套数组 | `const` 套 Array 是项目明令禁止的坑。 |

**理由**：调用点直接拿到 `int / bool / float / String`，无需转换；类型化数组下标有类型（`_BOSS_HP[i]` 在 `Array[int]` 上返回 `int`），不触发"未类型化 Array 下标无法推断"的坑。写法在本项目已被验证：`const COLOR_CN := [...]`（Game.gd:25）、`const POOL: Dictionary[int, Array]`（Boss.gd:24）、`static func` 里构建 `PackedStringArray([...])`（DifficultySelect.gd:99）。

**后果**：加一关 = 往若干张一维表里各加 1 个数；改数值不碰逻辑。**反转条件**：若单关参数超过 ~25 个、或出现"某关要临时覆盖某子系统的独立参数块"，则拆成「通用参数表 + 每关 override」。

## B. 怪物种类注册表（ADR-2）

### ADR-2：单 `Enemy` 类 + `kind` 枚举 + `EnemyBrain` 静态行为分发 + `Spawner` 工厂；独有怪**只改运动 / 开火 / 外形，不改配色**

**状态**：已决定；`EnemyKind` 已落地（7 种）

**决策**
1. `scripts/entities/EnemyKind.gd`：`enum K` = `GRUNT(0)` + 7 种独有怪；附带中文名表、横幅简称表、分值表、血量倍率表、**配额表**、中性色表、所属关卡表，以及三条硬闸常量。
2. `Enemy` 增加 `kind: int` / `stage: int` / `no_block_clear: bool`，**`setup()` 签名保持不变**（既有自测调用点零改动）。`_motion()` / `_firing()` 里 `kind == GRUNT` 走现有 `match pattern` / `match color`，其余转发 `EnemyBrain`。
3. `EnemyBrain.gd`：`static func move(e, delta)` / `static func fire(e)`，`match e.kind` 分发。
4. `Spawner.gd`：唯一出怪入口，`world` 显式注入（禁用 `get_parent`）。

**备选**：① 每怪一个子类 —— 工厂侧要 `match kind -> 脚本路径`，而脚本路径不能进 `const`（`PackedStringArray([...])` 都不能用于 const），只能写运行时字符串表，与 ADR-1 冲突；且 `Enemy` 186 行里行为差异只占 20%。② Callable 组合 —— `const Dictionary[int, Callable]` 未在本项目验证过，且断点打不进具体行为。③ 全塞进 `Enemy` —— 会膨胀到 450+ 行，拆 `EnemyBrain` 只是搬家、零语义变化。

**理由（关键）**：独有怪**不自带随机色**，色全部由 `Level` 从 S / S' 统一分配 —— 与 `Elite`（力场色 ∈ S）、`Boss`（护罩色 ∈ S）是同一条设计原则。**因此现有配色算法一行都不用动**，SelfTest 的配色断言不会因加怪而失效。

**后果**：`EnemyBrain` 会跨类读 `Enemy` 的内部字段（`_t / _base_y / _amp / _freq / _home_x / _leaving / _entered`）。**约定：这些字段是 Enemy 的内部契约，EnemyBrain 可读，其它类一律不许。**

## C. Boss 差异化（ADR-3，**已按触发条件修订**）

### ADR-3：基类 `Boss` + 配置驱动（L1~L3 / L5）+ **仅 L4 拆子类**

> **⚠ 修订（2026-09-22，主理人裁定 + 实测复核）**：原 ADR-3 写的是「L4 / L5 **各自**建子类」，
> **实际只拆了 L4**。L5 不拆，理由与量化依据见下方 **ADR-3.1**。此处标题已同步改为「仅 L4 拆子类」。

**状态**：已决定（按主理人裁定：**L4、L5 直接按"触发拆子类"处理，不要为了守住单类而把分支压进 60 行**）

**决策**
- `Boss.gd` 保留为**基类**（入场 / 巡游 `_move` / 受击 `hit` / `_check_phase` / `_check_enrage` / `_clear_bullets` / 死亡演出 / 护罩骨架），新增 `stage: int` / `title: String` / `boss_name: String`，**删掉 `const MAX_HP`**（血上限一律用实例变量 `max_hp = StageCfg.boss_hp(stage)`）。
- `BossCfg.gd` 提供 `pool(stage, phase) -> Array[String]` / `dur_of(skill) -> float` / `tick_of(skill) -> float`（带兜底）。
- **L1 / L2 / L3**：单类 + 每关技能池 + `traits` 位标志即可。
- **L4 深渊之喉**（子核心免伤 + 伤害共享 + 召唤 + 暴露期护罩）与 **L5 终焉号**（四相各独立技能组 + 独立护罩轮转）：**各自建子类** `Boss4 / Boss5 extends Boss`，只重写 4 个挂点。
- `phase_marks() -> Array[float]` 必须返回 **1~3 条可变刻度线**，HUD 不得写死两条。

**反转条件（原 ADR-3）**：traits > 6 个 或 单 Boss 独有分支 > 60 行 → 拆子类。

### ADR-3.1 **L4 拆 / L5 不拆** —— 决策与量化依据

**结论**：`Boss4.gd` 存在且已落地；**`Boss5.gd` 不存在，也不建**。

**量化依据（实测，不是估算）**

| 项 | 实测值 | 对照反转阈值（> 60 行） |
|---|---|---|
| `Boss.gd` 总行数 | **752 行** | — |
| 其中 **L5 专属分支** | **1 行**（`_cast_step()` 里 `grid_rain_blue` 的列数判据 `phase >= 3 or stage >= 5`） | 差 **两个数量级**，远未触发 |
| `Boss4.gd`（L4 子核心） | **311 行** | 超阈值 5 倍，**必须拆** |

**为什么 L5 不需要拆（性质不同，不是"懒得拆"）**

L4 与 L5 的差异化**载体不同**：

- **L4 的差异是有状态的** —— 子核心要持有「分裂数量 / 存活列表 / 剩余血量 / 召唤计时 / 暴露期计时 / 是否狂暴常驻」这一整套**运行时状态**，并在这套状态之间迁移（护罩期 → 暴露期 → 重新分裂）。状态必须被某个对象持有，所以只能独立成类。这部分写了 311 行。
- **L5 的差异是无状态的** —— 四相重构、每相独立技能组、护罩轮转，全部是 **`BossCfg._L5_P1.._L5_P4` + `StageCfg.phase_marks()` 里的静态数据**。基类读配置即可，一行分支都不用写（那唯一的 1 行还是为了修列数，属于参数校正而非行为分支）。

**这正是 ADR-3 想要的结果**：能用配置解决的就不要写分支。为 L5 拆一个空壳子类，等于把「数据驱动」倒退回「代码分支」，与 ADR-3 的方向相反。

**再次被问到时的回答口径**：先量 `Boss.gd` 里 L5 专属行数。只要它还是个位数，就不拆。什么时候它涨过 60 行，什么时候按反转条件拆。

**反转条件（针对本条）**：`Boss.gd` 中 L5 专属分支 > 60 行，或 L5 需要持有基类没有的运行时状态 → 建 `Boss5.gd`。`Level._make_boss()` 已按关号探测 `res://scripts/entities/Boss%d.gd`，届时**只需新增文件，不用改 Level**。

## D. 逐关解锁存档（ADR-4，已落地）

### ADR-4：另起 `user://progress.json`（带版本号），旧 `highscores.json` 只读不写不迁移不删除

**状态**：已决定并已落地

**决策**
- 新档 `user://progress.json`：`{"v": 2, "unlocked": int, "stages": {"L1": {...}, ...}}`。
- 关卡键 **`"L1".."L5"`**（非纯数字）。旧档键 `"0"/"1"/"2"` 是难度键，绝不能被读成关卡纪录（设计 §J.7 阻塞项，主理人已确认）。
- 版本不对 / 解析失败 / 结构不对 → **静默降级为「只解锁第 1 关，各关最高分 0」**，绝不因 IO 失败让游戏起不来。
- 旧档处置：首次启动（有旧档、无新档）时把 `highscores.json` 另存为 `user://highscores.legacy.json`；**不迁移、不删除、不展示**。旧纪录语义（难度最高分）与新纪录（关卡最高分）不可一一映射，迁移会污染纪录。
- **⚠ 但「完全不继承」也不是本 ADR 的决定 —— 解锁进度要继承，分数不继承。**（主理人明确裁定为**方案 A**，见下"解锁进度继承"小节。只写「不迁移」会让下一个人落成「方案 C：完全不继承」，那是错的。）

**备选与否决**：复用 `highscores.json` 换键 —— 旧档会被读成"第 1 关最高分 8000 / 已通关第 2 关"，玩家看到凭空出现的解锁进度。只存 `unlocked` 不存最高分 —— 两个文件双向依赖，"通关 + 破纪录"要写两次盘。

### ADR-4.1 解锁进度继承（**方案 A**，主理人裁定）

首次启动（**有旧档、无新档**）时，**读旧档各难度纪录的 `win` 字段**决定 `unlocked` 初值：

- **档 → 关映射**：简单 → L1 / 普通 → L2 / 困难 → L3。
- **某档有分数** → `unlocked = max(unlocked, 该档对应关号)`。
- **某档 `win == true`** → `unlocked = max(unlocked, 该档对应关号 + 1)`。
- **分数一律不迁移** —— 各关最高分一律从 0 开始（`stage_best` 全空）。

**为什么只继承解锁、不继承分数**：分数是"这一关打得怎么样"的度量，旧档它度量的是"某一档难度打得怎么样"，两者不同量纲、不同上限，搬过来会让玩家看到"我第 3 关已经 11780 分但我根本没打过第 3 关"。而 `win` 是**布尔事实**（"我确实打穿过某一档"），把它翻译成"我至少打到第 N 关"是保真映射，且只影响**哪些关卡可选**，不影响任何纪录展示。

**为什么封顶在 L3**：旧档只有三档，最高只能推出"打到第 3 关 + 通关过困难 → 解锁 L4"，不可能凭空推出 L5。`unlocked` 上限仍是 `STAGE_N`。

**否决的方案 B**：按旧档分数换算成各关分数（不可映射，见上）。
**否决的方案 C**：完全不继承（玩家打穿过困难，更新后要从第 1 关重打，等于抹掉既有进度 —— 这也是本小节存在的唯一理由）。
