## 1 · 整体基调：硬派军事 70% ／ 史诗浪漫 30%

### 1.1 推荐配比与理由

**推荐 70 : 30（硬派军事为主，史诗浪漫为辅）。**
（与 `04-文案风格指南.md` §2 定的文案语气 **6 : 4** 同向、略更偏硬派——
因为视觉层比文案层更直接地参与判定，浪漫预算要再收紧一点。）

理由不是审美偏好，是**可读性预算的零和性**：

弹幕射击的画面里，玩家每秒要做几十次「这颗弹是什么颜色 / 这个东西是敌是我」的判定。
每一分「美」花在**参与判定的图层**上，都要用「看得清」去还。而太空歌剧的浪漫感
（星云、星野、行星、晨昏线）几乎全部可以放在**不参与判定的背景层**——
而背景层恰好是本工程已优化过的那层（`Background.gd` 把绘制指令从 ~370 压到 ~105，
方式是烘焙成周期纹理，逐帧只做纹理平移）。

所以配比不是「掺多少浪漫」，而是**浪漫放在哪一层**：

| 图层 | 参与判定？ | 基调配比 | 说明 |
| --- | --- | --- | --- |
| **L2 判定层**：弹幕 / 护罩 / 特效 / 传感器 | ✅ 是 | **100% 硬派** | 几何锐利、边缘闭合、高对比、零装饰性曲线 |
| **L1 结构层**：我方战甲 / 敌方星盗 / 舰体 | ✅ 是（敌我识别） | **80% 硬派 + 20% 浪漫** | 装甲板 / 天线 = 硬派；拼装外露管线 / 改装件 = 浪漫 |
| **L0 氛围层**：星云 / 星野 / 行星 / 尘埃 | ❌ 否 | **20% 硬派 + 80% 浪漫** | 浪漫预算全部倾倒在这里，逐帧零成本 |
| **UI / HUD** | ❌ 否 | **70% 硬派 + 30% 浪漫** | 数据可读性优先；标题与结算可放开 |

一句话总判据：**浪漫只在玩家不需要做判断的地方发生。**

### 1.2 用数值守住这条配比（可复核，不靠眼睛）

把「背景不能抢弹幕」从一句口号变成一条**明度分层纪律**：

| 层 | 允许的相对亮度（sRGB 线性化后 Y） | 允许色相 |
| --- | --- | --- |
| **L0 氛围层** | **Y ≤ 0.15** | 自由（紫 / 品红 / 青 / 靛），但**禁止使用四档属性色的色相带** |
| **L1 结构层** | **0.15 < Y ≤ 0.45** | 中性灰（装甲）+ 本属性 DARK 档 |
| **L2 判定层** | **Y ≥ 0.24** | 四档属性色 MAIN/GLOW/CORE，高饱和 |

> **硬规则：任何 L0 元素不得进入 L2 的明度带（Y ≥ 0.24）。**
> 这一条同时解决了三个具体风险：
> 1. 星云不能亮到盖过红色弹（Y=0.24）——红弹是本作明度最低的弹，最容易被背景吃掉；
> 2. 星点不能亮成「近白实心圆」——否则与光子弹（白，Y=0.90）抢识别；
> 3. 行星盘面不能高过 Y=0.45——否则屏幕右侧 0.80W/0.20H 那块会变成视觉黑洞。

## 2 · 配色板

### 2.1 四档属性色：**结论 = 保持原数值不动，只改语义名**

> **答案先给：不改。** 下面是理由、实测数据与必做的补偿方案。

#### 2.1.1 现状数值（`Game.gd` COLOR_MAIN / GLOW / DARK / CORE，索引 0..3）

```gdscript
COLOR_MAIN := [Color(0.98,0.24,0.27), Color(0.22,0.62,1.00), Color(0.93,0.96,1.00), Color(1.00,0.80,0.14)]
COLOR_GLOW := [Color(1.00,0.56,0.24), Color(0.45,0.86,1.00), Color(0.84,0.92,1.00), Color(1.00,0.93,0.42)]
COLOR_DARK := [Color(0.40,0.04,0.09), Color(0.03,0.16,0.40), Color(0.28,0.32,0.42), Color(0.38,0.26,0.02)]
COLOR_CORE := [Color(1.00,0.94,0.80), Color(0.90,0.98,1.00), Color(1.00,1.00,1.00), Color(1.00,0.99,0.82)]
```

#### 2.1.2 实测：四档色在深空底上的对比度

背景天空实测落在 `#40458C` 一带（`Background.gd` 的 modulate 系数 0.42/0.45/0.62 所致），
其线性明度 **Y_bg ≈ 0.072**。四档 MAIN 的线性明度与对比比（WCAG 式 (L1+.05)/(L2+.05)）：

| 档 | 语义（假设） | sRGB | **线性明度 Y** | **vs 背景** | 备注 |
| --- | --- | --- | --- | --- | --- |
| 0 | 电浆（红） | (0.98,0.24,0.27) | **0.241** | **2.38 : 1** | 四档中最低——**已经踩在可读下限附近** |
| 1 | 寒霜（蓝） | (0.22,0.62,1.00) | **0.326** | **3.08 : 1** | |
| 3 | 引力（黄） | (1.00,0.80,0.14) | **0.646** | **5.70 : 1** | |
| 2 | 光子（白） | (0.93,0.96,1.00) | **0.904** | **7.82 : 1** | |

两两对比比（越大越好分）：

| 对 | 对比比 | 判定 |
| --- | --- | --- |
| 红 ↔ 蓝 | **1.29** | 明度接近 → 靠**色相**分（暖/冷，deutan/protan 均保留蓝-黄轴） |
| 黄 ↔ 白 | **1.37** | 明度接近 → 靠**彩度**分（黄饱和 / 白不饱和） |
| 蓝 ↔ 黄 | 1.85 | 够 |
| 蓝 ↔ 白 | 2.54 | 够 |
| 红 ↔ 黄 | 2.39 | 够 |
| 红 ↔ 白 | 3.28 | 够 |

#### 2.1.3 为什么不改（四条理由）

1. **红档已经是最低明度的一档（2.38:1），再压就掉出可读阈值。**
   想拉开「红↔蓝」的 1.29，直觉做法是压红——但红对背景只有 2.38:1，压到 2.0:1 以下
   在密集弹幕里就会开始「丢弹」。**这是本配色唯一不能动的方向。**

2. **抬黄会挤到白。** 黄↔白 已经只有 1.37，任何让黄更亮的调整都会让它俩糊成一片。

3. **当前四档对 deutan / protan 已经接近最优。**
   红-绿色盲（占色觉障碍 ~95%）保留的是**蓝-黄轴**。本配色在蓝-黄轴上的分布是
   「蓝（Y=0.33）· 白（中性亮）· 红/黄（暖亮）」，跨越冷暖两端，且白档提供了
   无彩度参照点。教科书式的色盲安全配色，本作已经基本满足。
   我实测验算过「红推橙」（`(0.98,0.24,0.27)` → `(1.00,0.36,0.18)`）：
   红档 Y 从 0.241 升到 0.291，与黄档的对比反而 **从 2.39 掉到 2.04**——**越改越坏**。

4. **改色值的连锁成本远高于收益。** 四张色表同时被 `build_robes.py`、
   `build_enemies.py`、`Boss._draw()`、`HUD.gd`、`Fx.gd`、`Danmaku.gd` 消费；
   且 `build_enemies.py` 的 `MAIN+GLOW ≥ 30%` 断言是按当前色值调过的
   （实测星盗 41.2% / 战将 37.6~39.7%，余量并不宽裕）。换色值 → 部件占比全部要重调。

> **结论：四档色值零改动。四档语义名由 design-strategist 定，工程侧只改注释与 UI 文案。**

#### 2.1.4 非颜色冗余通道（**v3 更新：已由四形异形弹天然达成，芯纹方案作废**）

上面表里有两对明度接近（红↔蓝 1.29、黄↔白 1.37）。对绝大多数玩家没问题
（靠色相 / 彩度分），但**完全色盲（~1/30000）与密集场余光读取**下会失守。

v2 曾为此规划「色觉辅助芯纹」（24×24 白模上镂空四形）。**RT-03 期间工程侧已把弹幕
恢复为四色四形异形 PNG**（火球/冰锥/灵环/符牌 → 科幻语义名见 07 §1.4.2），
按属性色绑死一形——**「颜色 + 形状」双通道编码零成本天然达成**，
芯纹方案**正式作废**，无需再排期。

遗留提醒：四形只解决「弹 vs 弹」的分辨；「我方弹 vs 敌方弹」（同色系）仍靠
形状 + 朝向 + 出处，不在此表范围内。（原 2.1.5 的 CB 调色板开关仍为 P2 可选，
优先级判断不变：不推荐优先做。）

#### 2.1.5 可选：CB 调色板开关（P2，**优先级低于芯纹**）

只在芯纹之外还想再加一层时才做。给出一组值供备选（deutan/protan 优化）：

```gdscript
# 仅色觉辅助开关打开时替换，默认不启用
COLOR_MAIN_CB := [
    Color(1.00, 0.42, 0.10),   # 电浆 → 朱橙（提亮、去品红，与蓝拉开）
    Color(0.20, 0.70, 1.00),   # 寒霜   → 亮青蓝
    Color(0.93, 0.96, 1.00),   # 光子   → 不变（白是唯一的无彩度参照点，动了损失最大）
    Color(1.00, 0.88, 0.30),   # 引力   → 明黄（提亮，与朱橙拉开）
]
```
**我不推荐优先做这个**：它只解决「红/黄」一对，不解决明度相邻（朱橙 Y≈0.29 vs 亮青蓝 Y≈0.33，
反而更挤）。**芯纹优先于调色板。**

#### 2.2.1 为什么把「固定肤色 SKIN」换成「驾驶舱玻璃 CANOPY」

`build_robes.py` 里 SKIN 是**恒定色、不随机体色走**，原注释的理由是：
> 「若脸也按袍色推导就会和袍身糊成一片，头直接『没了』—— 这个尺寸下头部是唯一能读出『人』的信息。」

战甲语境下「肤色」讲不通，但**这条纪律本身必须原样保留**：驾驶舱 / 传感器是
44×36 里唯一能读出「这是载具头部」的信息，同样不能随机体色走。

- 换色：`SKIN (1.00,0.87,0.72)` → **`CANOPY (0.62,0.86,0.98)`**（冷青玻璃）
- **几何零改动**：FACE / NOSE / EYE 区域原样保留，只换填色
- 与光子白 `MAIN (0.93,0.96,1.00)` 的区分：明度 0.80 vs 0.90，且舱盖面积固定 ~50px、
  位置固定在头部——**不会被误读为弹幕**（弹幕小、会动、形为环/团/锥/牌）
- 断言影响：07 §2 的「朝向断言 A」依赖这个固定色集合，换色后**像素集合不变、重心值不变**（实测 25.04），断言无需改阈值 ✅

## 3 · 像素风约束

全部沿用现有已验证的约定，**不新增、不改**：

| 项 | 约定 | 现状确认 |
| --- | --- | --- |
| 过滤 | `TEXTURE_FILTER_NEAREST`（`ArtAssets.make_sprite()` 统一设置） | ✅ 已在用 |
| Mipmap | **关闭**（`mipmaps/generate=false`） | ✅ 全部 .import 已确认 |
| 压缩 | **无损**（`compress/mode=0`） | ✅ 全部 .import 已确认——有损会在纯色块边缘产生污渍 |
| 烘焙比例 | 约 **1:1** 预烘焙，运行期不做连续缩放放大 | ✅ `ArtAssets.gd` 注释明载 |
| 描边 | 剪影外扩 **1px**，`MaxFilter(3)` + `ImageChops.subtract`，**只落在外侧不覆盖内部** | ✅ 两个 build 脚本同款实现 |
| 抖动 | **禁止 dithering / 渐变噪点** | 理由见下 |
| 旋转 | **禁止**（`Danmaku.setup()` 已把 `spin` 一律归零） | 理由见下 |
| 光照 | 默认**光从左上**（弹丸实测：左上高光、右下暗边，见 §4） | ✅ 沿用 |
| 整数倍率 | UI 立绘必须整数倍（择甲 3x / 战甲库 6x），**禁止连续缩放** | ✅ `ArmorArt.gd` 明载 |

**为什么禁止抖动**：像素素材在运行期会被非整数缩放（弹幕 `_art.scale = r/17`、
飞剑增攻放大）。抖动图案在非整数缩放 + NEAREST 下会变成逐帧爬行的噪点，
在每秒数百颗弹的密集场里是灾难。

**为什么禁止旋转**：NEAREST 下旋转像素图会边缘抖动（代码注释已记录）。
`Danmaku.setup()` 已把 spin 归零，**新增资产一律不得引入旋转动画**，
朝向全部靠烘焙固定。

## 4 · 敌我识别规则（新题材下的重新表述）

### 4.1 原规则与等价迁移

**原**：「朝左、头顶双角、轮廓带刺的是盗匪；朝右、平顶、轮廓闭合的是我（玩家修士）。」

**新（v2 · 用户已拍板精英 = 精英机 / 无人兵器）**：
> **朝右、有舱盖玻璃冷青色、穹顶单峰、轮廓对称闭合的是我（人形战甲）；
> 朝左、无舱盖色、顶带双联分离、轮廓非对称外露的是敌（无人兵器）。**

> ⚠️ **本条已按用户决策修订（RT-02b）。** 原 v1 方案的第一通道是
> 「生物 vs 机械」的阵营材质对立，敌方定生物星盗武装。用户选定精英 = 精英机后，
> **我方与场上威胁最大的敌方单位同为机械，该通道失效**。
> 补偿方案见 §4.2——替代元通道是**舱盖色的有无**，它比「生物 vs 机械」
> 更强，因为它可以被机器直接校验。

### 4.2 判据（修订版，从快到慢）

| 优先级 | 通道 | 我方（人形战甲 44×36） | 敌方（星盗机械：杂兵碰撞 r19 / 精英碰撞 r34 · 均为 `YokaiArt` 矢量） |
| --- | --- | --- | --- |
| **1（最快，主通道）** | **舱盖色的有无** | **有** `CANOPY (0.62,0.86,0.98)` 舱盖玻璃（约 50px，恒定不随机体色走） | **完全没有这个色**（无人 → 无驾驶舱 → 无舱盖） |
| **2** | **朝向** | 朝**右**（舱盖 / 前向探针朝屏幕右） | 朝**左**（光学窗 / 主炮朝屏幕左） |
| **3（兜底）** | **顶层轮廓** | 穹顶**单峰**，顶带 **1 段**，闭合无尖刺 | **双联挂架分离**，顶带 **≥2 段** |
| 4（加成，不作主通道） | **对称 vs 非对称** | 上下对称双炮管、对称肩甲、轮廓对称 | 单根**下挂**主炮、双挂架不等高、轮廓非对称 |
| 5（加成，不作主通道） | **体量** | 44×36 | 精英机碰撞 r34 / 造型 r≤40（vs 玩家 44×36、判定 r11 的**绝对体量压迫**） |

**为什么「舱盖色的有无」能顶替「生物 vs 机械」**：

它把一个**语义事实**（无人兵器没有驾驶员，所以没有驾驶舱）直接编码成了
**判别信息**——而且这是**唯一一条能被机器校验的元通道**：
PNG 资产走像素断言 H，敌方矢量活体（`YokaiArt.gd` / `Boss.gd`）走源码静态检查 V1
（见 07 §2.4）。相比之下「生物 vs 机械」只能靠人工看图保证。
实测：全部 8 张现存敌方 PNG 上 `CANOPY (158,219,250)` 的精确命中数 **= 0**；
玩家四型舱盖像素数 **= 50**；精英机新矢量几何中该色**根本不出现**。
**通道天然成立，零额外绘制成本。**

**为什么体量与非对称只能作加成**：

两者都只用作「主通道已判定后的置信加成」。

### 5.1 关于 #2 的复核结论（原预警已解除）

我在 v1 预警过「引力若定紫色会与寒霜蓝在色盲下撞车」。
design-strategist 最终定名**「引力」但把色值语义定为「引力场能量的金黄」**，
**四档色值一个都没动**——预警自动解除，无需任何返工。✅

「引力」在中文语境里常被联想为**紫罗兰 / 靛紫**。若最终定名走紫色，
第 3 档（黄）需改成紫——**我不推荐**：

- 紫色（如 `Color(0.72,0.38,0.95)`）在 **deutan / protan 下会被读成蓝色**，
  与「寒霜蓝」正面撞车 → 直接制造一对新的色盲混淆；
- 而当前的**黄色**在蓝-黄轴上与蓝、白都拉得开，是四档里最安全的一档；
- 且黄档对背景对比 5.70:1，是仅次于白的第二高，换成紫会显著下降。

**建议**：要么维持黄色并把语义名定为暖色词（引力井 / 重子 / 琥珀 / 重炮），
要么把「引力」这个名字让给别的档位。**不要为了名字改色值。**
