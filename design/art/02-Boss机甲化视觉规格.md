### 1.3 CANOPY 替代：Boss 侧三种「窗」表达

**统一构造（三者共用）**：`DARK` 底槽 → 内部 `NEUTRAL` 芯 → **无纯白描边** → **无 CORE 单点高光** → **≥3 枚成阵**。

| 方案 | 形态 | 尺寸规则 | 分配 |
|---|---|---|---|
| **A · 传感器阵列** | 矩形底槽 + 内嵌 N 枚等距矩形窗 | 底槽 `0.34r × 0.09r`；窗 `maxf(4,0.071r) × maxf(3,0.054r)`；间距 `0.10r`；N = 5（L1）/ 7（L5） | L1 熔核号、L5 终焉号 |
| **B · 舷窗列** | 沿舰体纵向的圆窗排 | 窗半径 `maxf(2.5, 0.045r)`；DARK 眼窝 = 窗半径 + 1.3px；间距 `0.14~0.16r`；N ≥ 4 | L2 霜噬号、L4 深渊之喉 |
| **C · 观察缝** | 单条水平狭缝（**不倾斜**） | `0.30r × maxf(3, 0.054r)`；DARK 填充 + 内嵌 `NEUTRAL` 芯（芯高 = 缝高 × 0.5） | L3 耀斑号 |

**为什么不与玩家混淆（四条，逐条可验）**：

1. **色**：窗芯恒 `NEUTRAL(0.74,0.78,0.86)`，`|B−R| = 0.12`；玩家 CANOPY `|B−R| = 0.36`，**差 3 倍**，且 CANOPY 明度更高、更饱和。
2. **数**：玩家 **1 枚**，Boss **≥3 枚成阵**。「一个大的」vs「一排小的」是纯形状判据，不依赖颜色。
3. **朝向**：玩家窗**朝 +X 前向倾斜**；Boss 窗**沿舰体纵向/横向排布，不朝前向**。玩家 +X 是头，Boss −X 是头 —— 朝向本就相反。
4. **装饰**：玩家窗有 **1.2px 纯白描边 + CORE 暖白高光 + 前向探针**三件套；Boss 窗**一件都没有**，只有 DARK 槽。

**候选色实测（写进 §6 门禁）**：`NEUTRAL(0.74,0.78,0.86)=0.12 ✅` / `STEEL(0.62,0.66,0.74)=0.12 ✅` / `STEEL_GLOW(0.84,0.88,0.96)=0.12 ✅` / `CORE[WHITE]=0.00 ✅` / `CORE[BLUE]=0.10 ✅` / `CORE[RED]=0.20 ❌` / `CORE[YELLOW]=0.18 ❌` / `GLOW[BLUE]=0.55 ❌` / `CANOPY=0.36 ❌`。
→ **结论：统一用 `NEUTRAL` 作窗芯，零判据风险，也读作「设备玻璃」而非「驾驶员座舱」。**

### 2.2 两个最坏场景的判据

| 场景 | 描述 | 三层判据（按优先级，任一层成立即判敌） |
|---|---|---|
| **A · 远距离** | Boss 刚入场，屏幕右缘 x≈1150，玩家 x≈230，间距 ~900px；Boss 只占 112~168px | ① **块面 > 100px 且连续** → 玩家本体最长边仅 40px，**永不** > 100px；② 实心块的**尖/钝朝向**：尖头朝左（−X）= 敌，舱盖朝右（+X）= 我；③ 右缘有推进焰（+X 尾焰）→ 敌（玩家无推进舱） |
| **B · 弹幕高峰** | 同屏数百颗弹（r≈5~9）压在 Boss 上 | ① **连续实心面积 ≥ 112px** —— 弹幕是离散小球，无法形成连续大面；② **有没有冷青 CANOPY** —— 有 = 我，无 = 敌（唯一一条颜色判据，且是「有/无」二值，不是「辨色」）；③ Boss 常驻 **8 段虚线护罩弧**（半径 ×1.70 ≥ 95px）—— 纯形状二值判据 |

> **新增强度校验**：机甲化后 Boss 部件密度上升，须复测「Boss 被弹幕覆盖时，≥112px 连续面是否仍然成立」。若某关装甲片分块把主体切得太碎，触发 §4.3 的描边补偿。

### 7.2 风险最高的一处实现难点

> **L4 深渊之喉：「机库闸门关闭」与「子核心 / 暴露期」三态联动的时序一致性。**

**四条叠加的理由**

1. **状态源在子类且是私有字段** —— `_cores` / `_exposed_win` / `_summon_t` 都是 `Boss4` 私有，`BossArt` 只能 `Object.get()` 读，读不到必须**降级画基础形态**（不能崩绘制）。一旦字段名变更，视觉会静默退化而门禁测不出来。
2. **三处绘制分属不同层** —— 闸门在 ⑥（BossArt 内）、能量索断裂在 ⑦c（`_l4_tethers`）、护罩弧在 ⑨（`Boss._draw()` 通用层）。三者必须**同一帧同相位**，否则会出现「闸门关了但护罩没开」或「能量索还在但护罩已开」的视觉矛盾 —— 而这两者传达的是**互斥的玩法信息**（「打子核心」vs「换甲破罩」）。
3. **相位切换会强制白送一次暴露期** —— `_on_phase()` 会清全部子核心，此时「子核心全灭」与「相位切换」同时触发，闸门/触须/护罩三层各有各的过渡动画，最容易在这一帧打架。
4. **狂暴后语义反转** —— 死锁防线让狂暴后每 4.5s **强制**开暴露期，而此时**子核心仍在场**。于是「闸门关闭（= 本体可打）」与「牵引臂绷紧连着子核心（= 打子核心）」会**同时显示**，与常规期的互斥语言冲突。

**建议的缓解口径（供工程参考，本轮不写代码）**：把「暴露期」定义为**单一布尔派生量**并由 `Boss4` 暴露一个**公开的、可 `get()` 的**字段（或一个 `is_exposed()` 方法），三个绘制层**都读它**，而不是各自从 `_cores.is_empty()` 推；狂暴强制暴露期时，牵引臂的能量索**保持断裂态**（与闸门语言一致），子核心仍在场这件事改由子核心**自身的绘制**表达，不再借牵引臂表达。
