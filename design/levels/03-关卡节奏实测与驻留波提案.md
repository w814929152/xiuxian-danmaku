## 0. 结论速览

| 提问 | 结论 |
|---|---|
| 关卡时长是否过短 | **不过短**。L1–L3 与设计目标吻合（60 / 84 / 90 s）；**L4 / L5 反而偏长 21~29%**，根因是 Boss 段（58 s / 63 s）远超设计的 21 s / 26 s |
| 关卡形式是否单一 | **属实**。五关结构完全一致、背景恒速滚动、敌人恒从右侧屏外飞入、运动模式只有 4 种 |
| 「清完怪物进下一波」要不要加 | **已经有了**，不是缺口（`Level.gd:470–474`）。真正缺的是**空间形式**这一种 |
| 要不要加「屏幕不滚动 + 刷怪」 | ✅ **已加**（2026-09-22），做成**每关 1–2 波的「驻留阵地波」**，不是整关停滚。见 §3 / 落地实况 §3.5 |

## 1. 时长：不算过短，L4 / L5 偏长

### 1.1 实测方法

波次那一半**能纯算**（`StageCfg` 的出怪间隔 × 格数是精确值），Boss 那一半**算不出来** ——
护罩轮转 / 散热窗口 / 相位壁 / 暴露期全是时间驱动的开关，平均倍率取决于战斗本身的时长，
只能跑一遍。故新增探针 `_selftest/PaceProbe.tscn`：

* DPS 外部注入，按 20 点成块命中（粒度理由见 §4 踩坑）
* 策略 A「完美换甲」：护罩色 ∈ 战甲时立刻切到该色（换甲无 CD，理论上限）
* 策略 B「不换甲」：恒用战甲[0]（设计 R4「不换甲能过但明显变慢」的下限）
* L4 一律「暴露期打本体 / 非暴露期打子核心」（最优解，裸打本体只有 20%）
* 探针玩家 100% 输出、永不走位、永不受伤 ⇒ **测出来的是下界，真实玩家只会更慢**

### 1.2 Boss 战 TTK（秒，游戏内时间）

| 关 | 设计 §F.1 | 实测 95 DPS 完美换甲 | 实测 152 DPS | 实测 95 DPS 不换甲 |
|:--:|:--:|:--:|:--:|:--:|
| L1 熔核号 | 12 | **16.8**（+40%） | 10.6 | 19.6 |
| L2 霜噬号 | 16 | **25.3**（+58%） | 15.8 | 25.3 |
| L3 耀斑号 | 19 | **19.2**（+1%） | 9.4 | 19.2 |
| L4 深渊之喉 | 21 | **58.1**（+177%） | 33.8 | 61.3 |
| L5 终焉号 | 26 | **63.2**（+143%） | 39.5 | 72.5 |

> 95 DPS = 单排光刃·零增幅（10 dmg ÷ 0.105 s）；152 DPS = 电浆剑甲双排（8×2 ÷ 0.105 s）。
> L2 / L3 无属性护罩，故「换甲 vs 不换甲」完全一致 —— 这是正确行为，不是漏测。

### 1.3 单关总时长

前置波次段取设计 §F.1 的估算值（含每波 6~15 s 清场，**未经实测**，依赖玩家水平）；
Boss 段取上表实测值。

| 关 | 前置波次（估算） | Boss（实测 95） | 合计 | 设计目标 | 偏差 |
|:--:|:--:|:--:|:--:|:--:|:--:|
| L1 | 43.9 | 16.8 | **60.7** | ~60 | +1% |
| L2 | 59.0 | 25.3 | **84.3** | ~80 | +5% |
| L3 | 71.0 | 19.2 | **90.2** | ~95 | −5% |
| L4 | 84.0 | 58.1 | **142.1** | ~110 | **+29%** |
| L5 | 94.6 | 63.2 | **157.8** | ~130 | **+21%** |

若玩家用电浆剑甲（152 DPS）：L4 → 117.8 s、L5 → 134.1 s，回到设计 ±7% 内。

### 1.4 三条判读

1. **「过短」不成立。** 最短的 L1 也有 ~60 s，五关合计 ~535 s（≈ 9 分钟）。
   真正的问题是**后两关偏长**，且偏长全部来自 Boss 段。
2. **根因：设计 §F.1 假设「有效 DPS 130~230」，与实际不符。** 零增幅基准只有 95，
   电浆剑甲双排 152。只有「电浆剑甲 + 捡到增幅核心」才够得着设计假设 —— 也就是说
   **设计文档把「满配玩家」当成了基准玩家**。
3. **换甲收益可量化**：L1 +17%、L5 +15%、L4 +5.5%。设计 R4「不换甲能过但明显变慢」成立，
   L1 / L5 的惩罚幅度（15~17%）是健康的。

### 1.5 🔴 顺带查出一处曲线断崖（与本次提问无关，但值得单独立项）

**L3 耀斑号的 Boss 战比 L2 还短 24%**（19.2 s vs 25.3 s），尽管血量多 33%。

原因：散热期 ×3.0 的收益压过了常驻减伤 70%。实测 L3 全程平均倍率 ≈ 1.75
（3200 HP ÷ (19.2 s × 95 DPS)）—— 也就是说「减伤 70%」这条设定被散热窗口完全抵消还倒贴。
阶段切换还白送两次 3.0 s 强制散热（相位刻度 0.34 / 0.67），光这两次就打掉
2 × 3.0 s × 285 DPS ≈ 1710 点，超过总血量一半。

**✅ 已修复（2026-09-22，主理人裁定「先修复再做」）** —— 两条都做了，不是二选一：

| # | 改动 | 落点 | 旧 → 新 |
|:--:|---|---|---|
| 1 | 散热倍率下调 | `StageCfg.heat_mul()` | 常态 **×3.0 → ×1.8**、狂暴 **×4.0 → ×2.4** |
| 2 | 阶段切换白送的窗口**按新阶段给**，不再恒取 P1 的 3.0 s | `Boss._on_phase()` | 硬编码 `heat_window(stage, 1)` → `heat_window(stage, phase)`（狂暴走 `heat_window_rage`）。两次切换合计 **6.0 s → 3.8 s**（P2 2.2 + P3 1.6） |

选 ×1.8 而不是 ×1.6：用手算模型（已用旧参数反推校准到 19.5 s ≈ 实测 19.2 s）扫过
1.6 / 1.8 / 2.0 三档，TTK 分别 ≈ 36.8 / **32.1** / 29.9 s。×1.8 落在 L2 25.3 s 与
L4 58.1 s 之间，单调递增成立，且单关总时长 ~103 s 相对设计 95 s 只偏长 8.5%
（是五关里偏离最小的）。散热占全程时间由 53.7% 降到约 40%，「常态 0.3 减伤」重新有意义。

**同步改动**：`MatrixProbe.gd` 的 `heat_mul` / 散热伤害断言（300 → 180），
新增一条元断言锁住「阶段切换不得硬编码 P1 窗口」（对改回硬编码敏感）；
总纲 §D.3 / §F.1、验收清单 §2.3 / §5、美术规格 L3 章节的倍率与时长表述全部订正。

## 2. 形式：单一属实，但缺口不是「清怪推进」

### 2.1 「清完怪物后进入下一波」已经存在

`Level.gd:470–474`：

```gdscript
var limit := StageCfg.clear_guard(stage, elite)
var guard := 0.0
while _running and guard < limit:
    await wait(0.3)
    guard += 0.3
    if _enemy_count() <= 1 and not _elite_alive():
        break
```

波次推进**本来就是清场制**，且星盗战将是硬性门槛（`_elite_alive()`）。
`no_block_clear` 单位（拆解者小片 / 引力雷 / L4 增援）不计入 —— 它们不阻塞清场。
所以用户担心的这件事不需要新增。

### 2.2 真正单一的地方

| 维度 | 现状 | 证据 |
|---|---|---|
| 关卡结构 | 五关一律「N 个清场波 → 1 个 Boss」，无任何第二种段落 | `Level._run()` |
| 背景 | **恒速滚动 46 px/s**，Boss 战降到 22 px/s，只有这一种模式 | `Background.gd:20 / :63` |
| 敌人入场 | **恒为 `x = VIEW_W + 70` 从右侧屏外飞入**，无第二种入场 | `Enemy.gd:53` |
| 运动模式 | 只有 straight / sine / dive（第 2 波起）+ 骚扰色恒 hover，共 4 种 | `Level._wave_moves()` |

所以「形式单一」的症结是**空间形式只有「持续向前推进」一种**，不是推进规则。

## 3. 驻留阵地波（Hold Wave）—— ✅ 已实施

### 3.1 形态

在**每关的 1–2 个波次**上启用，与推进波交替出现：

```
现状：  推进 → 推进 → 推进 → 推进 → Boss
建议：  推进 → 驻留 → 推进 → 驻留 → Boss
```

一个波次被标记为驻留时，改变三件事：

| 项 | 推进波（现状） | 驻留波（新增） |
|---|---|---|
| 背景滚动 | 46 px/s 恒速 | **8 px/s**（`Background.SCROLL_HOLD`；不取硬 0，理由见 §3.4） |
| 敌人入场 | 右侧屏外飞入 | **屏内跃迁入场**（x ∈ 屏宽 55%~95%，落一发跃迁环 + 白闪） |
| 清场判定 | 同现状 | **完全复用**，一行不改 |

### 3.2 编排建议

* **每关只插 1–2 波**，压在中后段（例如 L4 的第 3 / 第 5 波、L5 的第 2 / 第 4 波），
  形成「推进 → 驻留 → 推进 → 驻留」的节奏对比，而不是把整关变成阵地战。
* **不动 Boss 战**（Boss 战已经有自己的 22 px/s 慢滚，是第三种节奏，不用再改）。
* 驻留波天然适合放**骚扰色**（恒 hover、远驻放弹）—— 不滚动时它的压制感更强，
  正好补上「驻留 = 被围住」的语义。

### 3.3 实际改动面（2026-09-22 落地，约 70 行）

| 文件 | 实际改动 |
|---|---|
| `scripts/StageCfg.gd` | 新增 5×5 位表 `_HOLD` + 访问器 `wave_hold(s, n) -> bool`（与 `_GAP` / `_TARGET` 同族同口径） |
| `scripts/world/Background.gd` | 散落的 46 / 22 收成 `SCROLL_NORMAL` / `SCROLL_BOSS` / `SCROLL_HOLD` 三常量 —— 不收拢就会出现第三个裸数字 |
| `scripts/world/Level.gd` | `_wave()` 开头按 `wave_hold` 切滚速、清场后恢复；`_spawn_slot()` 加 `warp` 并算**整组共用**的跃迁 x；`_wave_banner()` 区分「驻留」；Boss 战改用 `Background.SCROLL_BOSS` |
| `scripts/entities/Spawner.gd` | `enemy()` 加 `warp_x := -1.0` 入参（**默认值即历史行为**，既有调用点零改动） |
| `scripts/entities/Enemy.gd` | `setup()` 加 `warp_x`：≥0 时落在该 x + 一发跃迁环 + 白闪 |
| `_selftest/SelfTest.gd` | 新增 `_test_hold_wave()` 13 条断言（位表 / 滚速 / 屏内跃迁 / 整组共用 x / 清场恢复 / 七种独有怪零回归） |

> **与原提案的一处偏差**：提案写的是 `warp := false` 布尔入参，落地改成 **`warp_x: float = -1.0`**。
> 原因：列阵者（L3 独有怪）1 格 = 3 艘成竖墙，**整组必须共用同一个 x** —— 各自随机会把墙拆散。
> 若只传 bool，`Enemy.setup()` 就得自己摇 x，组内三艘各摇一次即散。已由门禁断言锁住
> （「列阵组整组共用同一个跃迁 x」）。

### 3.4 风险与对策

* **停滚会让画面「死」。** `Background._off` 同时驱动星野 / 星云 / 小行星带，
  只有漂浮碎屑走 `_t` 仍在动。故建议**降到 0~10 px/s 而不是硬 0**，保留一点漂移感。
  若主理人能接受「静止星域 = 阵地战」的语义，硬 0 也成立。
* **屏内跃迁可能被读作「凭空出现」不公平。** 原对策是「跃迁前 0.4 s 画收缩警示环」，
  落地改成**落地那一帧画扩张跃迁环 + 白闪**（`Fx.ring` + `_flash = 0.28`）。
  理由：敌人落地后**开火仍有 0.7~1.5 s 天然宽限**（`_fire = 0.7 + randf()*0.8`），
  够玩家反应；而「提前 0.4 s 预告」要引入一段延迟 spawn 的状态，把出怪入口复杂化，
  收益不抵成本。与 L4 子核心暴露期的宣告环同一视觉语言。
* **对既有平衡的影响接近零**：只改入场位置与背景滚速，不改血量 / 弹幕 / 配色 / 计分。
  实测复跑 `PaceProbe`：五关 Boss TTK 与落地前完全一致（16.9 / 25.3 / 35.4 / 58.1 / 63.2 s）。
* 门禁：改完必跑 `运行自测.bat`，验收线仍是 **fails=0 且 ERROR=0 且 WARNING=0**。

## 4. 附：本次实测踩的坑（写探针的人必读）

第一次跑出来的数是**错的**，五个 Boss 的 TTK 全部退化成「血量 ÷ DPS」，
L1 / L5 的「完美换甲」与「不换甲」还得出一模一样的结果。

根因：`Boss.hit()` / `Boss4.hit()` 结尾都是 `maxi(1, int(roundf(dmg * mul)))` —— **下限 1**。
探针按帧打点时（headless ~145 fps，95 DPS → 每帧 0.65 点，累积出来 `n` 恒为 1）：

```
1 × 0.60（护罩异色） = 0.6 → roundf → 1 → maxi → 1
1 × 0.20（相位壁免伤 80%）= 0.2 → roundf → 0 → maxi → 1
1 × 0.30（常驻减伤 70%） = 0.3 → roundf → 0 → maxi → 1
```

**护罩 / 相位壁 / 常驻减伤三条倍率被这个下限全抹平。** 真实光刃单发 10 点
（×0.6 = 6）不受影响 —— 这是**探针的**粒度问题，不是游戏的。

修法：按 `HIT_CHUNK = 20` 成块打（20 × 0.6 = 12 整，倍率误差 ≤ 2.8%）。
另用 `Engine.time_scale = 6.0` 把 15 次测量的墙钟从 ~10 分钟压到 ~2 分钟
（游戏内时间照常走，机制计时同步放大，纯 delta 驱动不受影响）。

诊断工具留在 `_selftest/WardDiag.tscn`，它每 0.5 s 采样一次 `ward / player_armors / _ward_t`，
就是它把这个疑问钉死的。

**推论（对任何自动化伤害探针通用）**：被测函数只要有「最低 1 点」之类的下限，
打点粒度就必须大于 1/最小倍率，否则测出来的是下限本身而不是倍率。
